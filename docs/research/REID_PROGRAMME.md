## 0. Why, and what TP-30 left
TP-30 (FD-01-D44) found every representation re-identifiable above chance, but with parameters from the
experiment's own generator and public seeds (review R2-01). It is not a test of operational blinding.
The programme answers four questions in order. A phase starts only after the previous phase's result is
recorded:

| Phase | Question | Output |
|---|---|---|
| RIP-1 | Does re-ID survive when parameters are drawn and held by Custody/Vault and the attacker is isolated? Per representation; independent samples and same-family pools; with and without ledger access. | measured accuracies, access-log audit |
| RIP-2 | Where does the leak come from in each representation: the representation itself, the blinding, or their interaction? Which statistics carry it? | leakage map (dev data only) |
| RIP-3 | Which hardening alternatives exist, what each one costs in research information, and how they compare? | alternatives table with costs, no test-set use |
| RIP-4 | Re-measure each selected alternative with its own pre-registered protocol and independent attackers; report everything. | privacy × utility results; evidence for CS-01-04 |

## 1. Facts from the code and sources that shape RIP-1 (checked before writing)
- `Vault.set_params(family, c, a, b, m)` stores the secret parameters with a salted commitment (س 213). **No
  code draws them**: the caller supplies values. The drawing method and the parameter distributions are
  «غير معرّف في المعمارية». RIP-1 must add a custody-side draw from the OS CSPRNG (`secrets.SystemRandom`).
- `access()` has no item for parameters. Only `symbol:` (G-Z operator) and `truth:` (court operator after the
  seal) exist. Parameters therefore never leave the vault through the access path, not even to custody's
  requesters. Blinding must run inside the custody executor, which holds the Vault object.
- Δ (tick step) is written **in the ledger** in `params_fixed` (`delta`) for every family, not in the vault.
  The ledger is readable by audit replicas. Δ equals the asset's tick in the synthetic world, so the public
  ledger may reveal the asset. This is a hypothesis RIP-1 tests (H4); it is not assumed.
- The `log_returns` scale is "estimated from Discovery" (س 205). It is not a secret parameter in the sources.
  TP-30 treated it as a secret random scale; that was a design choice outside the sources and is corrected
  here. `activity_time` and `volatility_time` have no secret parameters at all.
  → Vault-mediated representations: `tick_grid` (c; Δ public), `level_residual` (m), `affine_level` (a, b).
  The other three carry no secret. They are still measured, as pure representation leakage.
- Parameters are fixed per claim family across slices (س 258, س 491). Several samples under one family is
  therefore the **normal operational case**, not an edge case: pooling is a primary scenario.

## 2. RIP-1 hypotheses (stated before the run; any outcome is reported)
- H1 (descriptive only, no test of equality; review R1-04): per representation, RIP-1 accuracy is set beside
  TP-30's interval with a comparability flag (§3.9). No statement "equivalent" or "different" is made.
- H2 (descriptive only; review R2-03): family-level accuracy with intervals is reported for g = 1, 4, 16. No
  monotone trend is claimed; a trend test, if needed, gets its own registration later.
- H3: the three representations without a secret leak as in TP-30, since blinding cannot act on them.
- H4: in V1 the public ledger adds identifying information. Δ is recorded per family for **every**
  representation (`params_fixed` requires Δ > 0), so it may reveal the asset for all six, not only tick_grid.
  No field is assumed to be the only channel (§3.6).
- H5 (security, pass/fail, OS-level; review R1-01): inside the isolation boundary of §3.7, the attacker
  cannot read the vault file, the key, custody memory or environment, the truth or the labels, cannot see
  custody processes, and has no network. Every probe in §3.7 must return "denied/absent". H5 covers this
  boundary on this host only; it is **not** a proof against kernel-level attacks or other hosts (declared).

## 3. RIP-1 design
**3.1 World (custody side).** Same 4 assets × 4 periods and generator as TP-30 (`reid.simulate`, frozen
code). The path RNG seed of each sample comes from `secrets.randbits(64)` and is stored with the labels as
hidden truth in the vault (`store_truth`). Paths are not reproducible without the vault, by design.

**3.2 What the ledger holds (review R1-02, closed).** `params_fixed` holds exactly: `family` (random UUID4),
`params_commitment` (salted SHA-256, 64 hex), `delta` (Δ = the asset's tick, as required by the code),
`epoch`, plus the signature envelope (identity, action, nonce, time). **Never** c, a, b, m, salts, seeds,
labels, prices or the key. `role_assigned`, `access_logged` (output hash only) and `submissions_sealed`
(hash only) are the other kinds in the run ledger. A test scans the ledger bytes for every secret value in
the vault (decimal repr and hex of the float) and for every label string; any hit is a critical failure.

**3.3 Parameter draws (review R1-03; frozen table).** One draw per family, from `secrets.SystemRandom()`
(OS CSPRNG). The four values are drawn independently of each other and of the path. Each representation
gets its own families (no family shared across representations). Every family stores all four values
(`Vault.set_params` needs c, a, b, m); a representation uses only its own.

| Param | Used by | Distribution (known to the attacker) | Range | Note |
|---|---|---|---|---|
| c | tick_grid | U(−1, 1) × L_asset | (−L, L) | L_asset = asset base level (1800, 30, 1.1, 150). TP-30 used × max(path); changed: no path dependence |
| a | affine_level | exp(U(−3, 3)) | (0.0498, 20.09) | a > 0 by construction (س 208) |
| b | affine_level | U(−1000, 1000) | (−1000, 1000) | as TP-30 |
| m | level_residual | choice{0.5, 1, 5, 10} × 100 × tick_asset | 4 values per asset | as TP-30 |
| scale | log_returns | none: not a secret (س 205, estimated from Discovery); no Discovery slice in this run, so unscaled | — | TP-30 drew a secret scale; corrected. log_returns therefore equals activity_time here (declared) |

Invalid values: impossible by construction (a > 0, m > 0, all finite); `Vault.set_params` still validates;
any refusal **aborts** the run (no re-draw). Commitment: existing `commitment(v, salt)` with a 16-byte salt
from `os.urandom`; the vault keeps values and salt; the ledger keeps only the commitment.

**3.4 Scenarios and units (review R1-05).** Grouping is visible in V0 and V1 alike (review answer to §6-1).
- S-ind: 1 sample per family, 25 families per class → 400 units; unit = sample = family.
- S-pool g = 4: 10 families per class → 160 units; g = 16: 5 families per class → 80 units (data size: all
  blinded data are committed); **unit = family**; one prediction per
  family; Wilson 95 % over families only. Sample-level accuracy may be shown descriptively, without an interval.

**3.5 Attackers (frozen before the test run).** Development data are the attacker's own simulations of the
public world description, with its own draws from the §3.3 table; dev families are built with the same g as
the scenario. Dev size: 25 families per class (S-ind), 10 per class (S-pool).
- A1, A2, A3: unchanged from TP-30 (same code hash), S-ind only.
- A4 (pooled, S-pool): per sample the A1/A2 feature vector, standardised with dev per-sample statistics.
  A4a = nearest class centroid on the **group mean** of these vectors (centroids from dev group means).
  A4b = majority vote of A2's per-sample predictions; a tie is broken by the smallest sum of distances to the
  tied centroids, then by the lowest class index (deterministic). Prediction is per family.
- A5 (V1, ledger channels; review R1-06). The visible field list is frozen as the ledger snapshot taken when
  the attacker starts (roles, `params_fixed` fields of §3.2, signature envelopes); the attacker enumerates it
  and records it. Variants: A5-Δ (Δ alone: class rule learned from dev); A5-f for **each** other public field
  alone (same rule, field as a categorical/numeric key); A5-all (all ledger fields); A5-comb (all ledger
  fields + A2 series features); in S-pool, A5-comb at family level (grouping exploited).
- A6 (marginal likelihood over the published priors; specified by the reviewer, implemented by Claude; code
  `rip1_attack.py` sent before the freeze; full derivation in its A6 comment block). Numerical integration is
  deterministic midpoint quadrature (G = 257) over the prior, not Monte Carlo; a (affine) is integrated in closed
  form; m is an exact 4-term sum. For class k, the marginal likelihood:
  L_k(x) = mean over θ ~ prior of p(x | k, θ), with p the Gaussian return model of the world (drift, vol,
  period factor, activity pattern) mapped through the representation:
  log_returns/activity_time: r directly; volatility_time: increments = r² (scaled χ²₁);
  affine_level (code: x = a·P + b, so P = (x − b)/a): r_t = ln((x_t − b)/(x_{t−1} − b)) exactly given b, a cancels;
  Jacobians 1/(x_t − b) included; x_0 term from ln a ~ U(−3, 3); tick_grid: P_t = c + Δ·x_t, r_t = ln(P_t / P_{t−1}),
  Jacobians Δ/P_t, grid points giving P ≤ 0 get likelihood 0, x_0 term from the lognormal P_0; level_residual: wrapped-normal increments given m with
  ΔP_t ≈ Lg·r_t (level held at Lg: approximation, declared), x_0 term = Σ_j lognormal(x_0 + j·m). In S-pool: L_k(group) = mean over θ of Π_i p(x_i | k, θ), with the members sharing θ.
  In V1: Δ conditions the draw (Δ is known); other ledger fields are used as by A5-all. Log-sum-exp throughout.
  Tick rounding of the world is ignored by the model (declared approximation).
Predictions are signed by reid_checker over {data_sha256, predictions}; the court operator seals their hash.

**3.5a Changes made while writing the code (for review before the freeze).**
- activity_time is not run separately: in this world it is byte-identical to log_returns (one update per
  step); the log_returns result is reported under both names. Five data sets.
- A5 development data: custody creates separate DEV families through the same pipeline (ledger records only,
  no series; their parameters stay secret) and gives their labels to the attacker as public training families.
  Without labelled ledger examples no unknown ledger channel could be learned. A5-f covers every field of the
  `params_fixed` entry: entry seq (and its rank in the ledger), prev, digest, signer, signature and every
  statement field. Numeric fields with more than 16 distinct dev values are binned into 8 quantile bins; naive
  Bayes with Laplace α = 1; an unseen value carries no information. A5-comb = NB log-posterior − ½·squared
  distance to the A2 centroid (S-ind) or the A4a group-mean centroid (S-pool).
- Family creation order across representations, scenarios, test and dev is shuffled by the CSPRNG, so ledger
  order carries no class information by construction (measured anyway by A5-f on seq).
- After scoring, the revealed truth (labels and path seeds) is committed. Each value is bound to the ledger
  through the hash in its `access_logged` record. The V1 ledger snapshot and the final ledger are both committed
  (the snapshot must be a prefix of the final ledger).
- Committed data are about 60 MB (blinded series npz, gzip ledgers, submissions).
- Smoke runs used throwaway families at n = 128 (declared). They cannot touch the test set, which does not
  exist before the run.

**3.5b Run structure after review R3.**
- One sandbox run = one representation × one view: 10 runs. Each run sees only that representation's data
  (plus the ledger snapshot in V1). A multi-representation attacker is not part of RIP-1; it is not measured,
  and no result may be read as covering it.
- Per run: a fresh input directory (root-owned, files 644, dirs 755: readable, not writable) and a separate
  output directory owned by the attacker (the only writable path). The public code is a separate root-owned
  read-only copy. Input hashes are taken before and after each run; any change aborts. A finished run's
  directory is closed (root, 700) and hidden by tmpfs from every later run.
- Shared writable directories (/tmp, /var/tmp, /run/lock, /dev/shm, /dev/mqueue, /var/lib/php/sessions) are
  hidden by tmpfs in the attacker's mount namespace. A probe walks the file system and requires that no
  directory outside the run's output directory is writable, and that the input files cannot be modified.
- The attacker holds no key and signs nothing (review R3-03). The trusted orchestrator verifies the input
  hashes and the prediction file, then signs a submission record per run with the reid_checker identity key.
  This is a role attestation by the orchestrator over the hashes it verified. It does **not** prove the
  attacker's execution integrity (declared). The seal covers the hash of all ten records.
- Ledger scan: every vault secret is passed (c, a, b, m, salt, seed, key). A value whose text equals a public
  value already in the ledger (Δ) cannot be told apart from it; such values are counted and reported as
  excluded, by kind (review R3-04). In smoke runs, some m values coincide with Δ texts and are reported this way.
- The results carry an explicit alias entry: activity_time has the same result as log_returns, is not an
  independent experiment and does not add to any sample size (review R3-05).

**3.5c Execution hardening after review R4** (`rip1.sandbox_run`, `read_output`, `validate_predictions`,
`reproduce_in_sandbox`).
- The run's input directory and the code copy are bind-mounted **read-only** inside the attacker's mount
  namespace (as root, before the privilege drop), in addition to root ownership and file modes.
- Every attacker process ends before the output is read: the attacker is PID 1 of its own PID namespace, so
  the kernel kills every remaining process when it exits; the orchestrator then checks /proc for any process
  of the attacker uid (must be none), takes the output directory back (root, 700) and only then reads it.
- The output is untrusted data: the directory must hold exactly one plain regular file `predictions.json`
  (no symlink, no hard link, no other entry), at most 64 MB, opened with O_NOFOLLOW, then a strict schema:
  exact top-level keys (so no self-made signature), the run's own view and representation, all probes passed,
  input hashes equal to the orchestrator's, the registered attacker names only, exactly the run's test
  families, labels as two in-range integers.
- The attacker-side code (copied package + script) imports no signing library and none of the system's
  identity, custody, ledger or charter modules (static test); the signing module is not in the copy.
- The per-run record signed by the orchestrator for the reid_checker role holds: run id, view,
  representation, input hashes, prediction hash, return code, leftover processes (0), inputs unchanged, probes
  passed and their hash, code hashes, Python and numpy versions. It documents what the orchestrator verified;
  it is not an absolute proof of execution integrity.
- Protocol reproduction: `reproduce_in_sandbox` rebuilds the ten runs from the committed data in the original
  order and with the same hiding, re-runs the attacker in a fresh sandbox per run, and requires (criterion
  fixed in advance) identical input hashes, code hashes, Python and numpy versions, all probes passing, no
  leftover process, unchanged inputs and exactly identical predictions; any difference raises. It needs root,
  so it runs on the run host. CI (not root) runs the direct recomputation instead. The attacker's only
  randomness is its development-set generator, seeded from the public `attacker_dev_seed` (no secret involved).
- Complete attacker set (review R5): `rip1_attack.expected_attackers(view, scenario, representation)` is the
  frozen set; the output must name exactly it per scenario (no attacker missing, none added). The A5-f names
  come from the frozen `LEDGER_FIELDS` list (11 fields; A5-f for the 10 other than Δ), not from the data or
  the output; the attacker uses that list and stops if the ledger rows expose anything else, and the
  orchestrator checks the real snapshot against it before any V1 run. Per run: V0 S-ind 4 attackers, V0 S-pool
  3, V1 14 per scenario (52 result rows per representation, 260 in all). The same validation is applied to the
  committed predictions and to every reproduced run.
- Adversarial tests run a hostile attacker in the real sandbox (§5 of the closure report,
  docs/audit/RIP1_R4_closure.md).

**3.6 Views.** V0: blinded series + family grouping. V1: V0 + the read-only ledger snapshot.

**3.7 Isolation boundary and probes (review R1-01; OS-level).** Host: Linux (Ubuntu 24.04, kernel 6.18),
custody runs as root. The attacker runs:
- as a dedicated unprivileged user created for the run (`rip_attacker`, no groups, no sudo), via
  `setpriv --reuid --regid --clear-groups --no-new-privs`;
- inside `unshare --net --mount --pid --fork --mount-proc`: own network namespace with no interface up,
  own PID namespace with a fresh /proc (custody processes not visible), private mounts;
- with `close_fds=True`, an empty environment except PATH, and a working directory owned by `rip_attacker`
  holding only the input file(s).
Custody side: the key exists only in the custody process memory (never written); the vault file and the
custody work directory are root-owned, mode 600 / 700; the ledger directory is 700 in V0 (V1 gets a copy).
Hidden in the attacker's mount namespace by empty tmpfs (mode 000): /home, /root, /tmp, /mnt, /var/tmp and the
custody directory. Order in code (`rip1.sandbox_argv`, review R2-02): (1) root creates the namespaces
(`unshare`), (2) still root inside them, `sh` mounts the hiding tmpfs, (3) `setpriv` drops uid, gid, groups and
all capabilities and sets no_new_privs, (4) `env -i` and `python -I` start the attacker. The order is tested
(test_sandbox_order_namespaces_then_drop_then_python), and the probes ran inside a real sandbox on this host
(test_isolation_probes_pass_inside_the_sandbox; smoke runs: all probes passed in V0 and V1).
Probes run inside the attacker process before the attack, results hashed into the record; each must fail:
read vault file; list custody dir; read run ledger dir (V0); open any other /proc/<pid>; ptrace attach (no
target visible); outbound TCP and UDP to a public address; loopback in the attacker's namespace is separate from
custody's; inherited file descriptors beyond 0–2; uid 0 / any capability in the effective set; sudo.
Plus a recorded listing (paths only, no content) of every non-system path the attacker user can read
under /, checked against the custody, vault and ledger paths: none may appear.
Declared limits: same kernel and host; root custody; not a defence against kernel exploits; Linux-only.
The probes run during the run (needs root). A CI test re-runs the probe harness on Ubuntu when
passwordless root/sudo is available and reports "skipped" otherwise.
Content scans of the input file (only floats, UUIDs, grouping; no label/seed/parameter strings) are
**input-sanity checks**, not evidence of no leak: whether the numbers leak is what the measurement itself
answers (review R1-08).

**3.8 Scoring.** After the seal, the court operator requests `truth:<family>` through `access()` (the
after-seal path; each read logged with the returned value's hash). Metrics per representation × scenario ×
view × attacker: top-1 accuracy for asset (chance 1/4), period (1/4), joint (1/16); counts; Wilson 95 % over
units; confusion matrices. No threshold.

**3.9 Comparability with TP-30 (H1 flags).** activity_time, volatility_time, level_residual, affine_level:
same transforms and parameter distributions, new world draws → comparable descriptively. tick_grid: c
distribution changed → partly comparable. log_returns: secret scale removed → **not comparable**.

**3.10 Reproducibility and binding (review R1-09).** Recorded: Python version, `env/test.lock.txt` sha256,
`pip freeze` output and its sha256, sha256 of every code file used (custody, attacker, probes), data schema
version, attacker configuration. Binding chain: each blinded data file's sha256 is inside the attacker's
signed submission; the submission hash is in the ledger (`submissions_sealed`); every revealed label's hash is
in the ledger (`access_logged.returned`); the ledger file, vault ciphertext hash and all data files are
committed. The heavy reproduction test re-verifies the chain, re-runs every attacker on the committed data
and re-scores. A6 needs numpy for speed: numpy is added pinned to the test lock (recorded as a decision).

## 4. Plans for later phases (each pre-registered before it runs)
**RIP-2 diagnosis (dev-side data only; review R1-07).** Paired factorial on the **same underlying paths, same
split, same attackers, same sizes**: conditions C0 raw prices (no representation, no secret), C1
representation with fixed public canonical parameters (c = 0, a = 1, b = 0, m = median of the m set), C2
representation with Vault-drawn secrets. Representation effect = acc(C0) − acc(C1); blinding effect =
acc(C1) − acc(C2); both as paired differences with a paired bootstrap over units. Interaction needs the fourth
cell "secret without representation"; where that cell is not definable for a transform, the interaction is
declared not identifiable rather than computed. Plus invariance analysis per transform and feature-group
ablation / permutation importance (groups: distribution, dependence, spectrum, volatility/extremes,
shape/sequence, ledger). Exact cells and estimators are frozen in RIP-2's own registration.

**RIP-3 alternatives (review R1-10).** Candidates (none chosen in advance): per-family volatility
standardisation; rank/quantile transform; Δ moved from the ledger into the vault, or Δ-normalised ticks;
per-sample m; calibrated dithering; time-warp or subsampling; asset mixtures. RIP-3 does **not start** before
its registration fixes the research-utility measures (operational: detection power for planted structures —
path-1 style planted effects, tick discreteness, volatility clustering — each with its test, sizes and
comparison method), so that a candidate that hides identity by destroying needed structure is reported as such.

**RIP-4 re-measurement.** For each selected alternative, a protocol in RIP-1's form: separate dev and test
data, frozen attackers including at least one not specified by Claude, no change after the test result, all
results reported. The privacy × utility table is the evidence for CS-01-04.
